### P1-3 `_texts` 五处重复定义 + 语义漂移

```
tasks/base.py:267          def _texts(self, items, min_conf: float = 0.5)
tasks/arena.py:98          def _texts(self, items, min_conf: float = 0.5)
tasks/dream_realm.py:83    def _texts(self, items, min_conf: float = 0.6)   ← 阈值不同！
tasks/goddess_trial.py:189 def _texts(self, items, min_conf: float = 0.5)
tasks/screen_registry.py:67  def _texts(items, conf: float = 0.5)            ← 无 self，签名也不同
```

**问题**：同一语义的方法有 5 份实现，其中 `dream_realm` 默认阈值是 0.6。调用方不显式传参时行为**因模块而异** —— 这类"同义不同默认"最容易演变成"某任务突然识别不到"的疑难 bug。

**建议**：只保留 `base.py` 的一份，其余改调用；`dream_realm` 若确需 0.6，改为**调用点显式传参**并注释原因（意图写在调用处，而不是藏在定义里）。

**预期收益**：消除 5 处同步维护成本；杜绝"改了一处忘了另四处"。

### P1-5 同一层内同类方法各自实现

`_click_text`（labyrinth 自建）、`_click_text_kw`（goddess_trial 自建）、`_click_template`、`_read_essence`、`_card_quality` 均为单模块私有实现，共 5 个"点击文本并重试"的变体。

**建议**：抽到 `base.py` 作为受保护方法（`_click_text_with_retry`），各任务只传判据与重试策略。**仅收敛签名一致的**，签名差异大的保留（避免强行统一引入 bug）。

### 结构上做得好的地方（不建议动）

- **分层清晰**：`infra`（截图/输入/识别）→ `services`（界面识别/导航）→ `auto_farm`（业务循环），职责边界真实存在，不是名义分层
- **契约明确**：`BaseTask` 定义了 `preflight` / `startup_probe` / `_stop_result` 三态契约，11 个任务都遵守
- **单一真相源**：版本号（`afk_bot/config.py`）、界面判据（`screen_registry.py`）、导航关系（`nav_planner.NAV_EDGES`）都做到了唯一来源
- **注释质量高**：绝大多数"为什么这么写"都有历史真机时间戳+现象记录，是本项目最有价值的资产之一

## 二、性能与资源消耗

### P1-1 引擎层裸 `time.sleep` 绕过可中断休眠（**用户可感知**）

任务层已修复（`BaseTask._sleep` 改为 0.1s 分段可中断），但**引擎层未跟进**：

| 位置 | 裸 sleep 数 | 说明 |
|---|---|---|
| `afk_bot/auto_farm/formation.py` | **25** | 编队/备战序列，累积可达数秒 |
| `afk_bot/infra/input.py` | **13** | click/drag 后的固定等待 |
| `afk_bot/infra/screen.py` | **10** | 截图等待 |
| `afk_bot/auto_farm/battle.py` | **9** | 战斗轮询 |
| `afk_bot/auto_farm/loop.py` | 3 | 主循环 |
| 其他 | 6 | — |
| **合计** | **66** | 全部不可中断 |

**影响**：点「停止」后，若正好落在 `formation.py` 的连续等待里，仍要等数百毫秒到数秒才响应 —— **与用户明确要求过的"停止要即时"存在残留落差**。

**建议**：`battle.py:111-128` 已有一份 0.1s 分段实现，把它提取为 `afk_bot/infra/` 下的公共 `interruptible_sleep(stop_fn, sec)`，替换上述 66 处（优先 `formation.py` 的 25 处 + `input.py` 的 13 处，这两处占比 58%）。

**预期收益**：停止响应最坏延迟从数秒降到 **≤0.1s**；顺带让这 66 处具备统一的"可被打断"语义。

### P2-3 日志文件无轮转

- `_afk_gui_log.txt`：`afk_gui.py:164` 以 `buffering=1`（**逐行 flush**）+ `'a'` 模式打开，**永久追加、无大小上限、无按天切分**
- 实测：7 天（170.6 小时）累积 **2.8MB / 30,985 行**，约 400KB/周、20MB/年
- 每行日志 = 1 次 write 系统调用（line-buffered）→ 在 22.7% 冗余行的情况下，**约 1/4 的磁盘写入是无效的**

**建议**：① 按天切分或超过 N MB 滚动（保留最近 5 个文件）；② 逐行 flush 改为批量 flush（利用已有的 200ms `_flush` 节流，`afk_gui.py:1653`）—— 崩溃时最坏丢失 200ms 日志，可接受。

**预期收益**：日志目录不再无限增长；磁盘写入次数下降约 **20~25%**。

### 性能上已经做对的地方（**不建议再优化**）

- **`template_match` 调用点 33 处，其中 30 处已限定 `region`/`scale_range`** —— 只有 3 处走默认 16 尺度全屏扫描。这个历史老大难问题（单次 ~2.5s）基本已经收敛，**无需再动**
- 战斗跳过按钮已拆成"高频模板 + 低频 OCR"双频子循环（`labyrinth.py`），采样率问题已解决

> ⚠️ 提醒：不要为了"性能"去改这两个已经优化好的部分，收益低、回归风险高。

  ⚠️ **修正**：本报告初版写"去重后本可只有 26 行、可省 7,003 行" —— 该估算不成立：
  振荡状态之间有**时间间隔**，做不到完全去重。**实测（按真实时间戳模拟限流）**：
  10s 限流 → 7,542 降到 **3,246 行**（家族 **−57.0%**、全日志 **−13.9%**）；
  15s → 2,443 行（−67.6% / −16.4%）。**已按 10s 实施**。
- **前 20 种模式合计占 53.3%** —— 日志熵极低
- 注意：**连续重复只有 2.2%**，说明冗余是**振荡型**（unknown → door → battle_prep → unknown…），单纯"与前一行比对"无法消除，必须做**状态变化检测**

**产生点**：`tasks/labyrinth.py:1013`、`tasks/goddess_trial.py:426`（每轮 OCR 打一条）

**建议**：新增 `BaseTask.log_state(key, msg)`，同一 `key` 只在**变化时**打印；另加**心跳**（每 30s 或每 50 帧补打一次），避免用户以为卡死。

```python
def log_state(self, key: str, msg: str) -> None:
    """状态类日志：同一状态只在变化时打印（防轮询刷屏）。"""
    if getattr(self, '_last_state_key', None) == key:
        return
    self._last_state_key = key
    self.log(msg)
```

**预期收益**：日志量 **-23%**，且关键事件（点击/成功/警告）从噪声中"浮出来"。对使用者最直接的价值是：**故障时贴给我的一段日志，有用信息密度从 ~1/3 提升到 ~1/2**。

### P1-2 ~~日志两套出口、两套词汇~~ → **已核实：该问题不存在（未改动）**

> **修正（实施阶段实测推翻）**：按"行形状"对 30,985 行做统计，任务级格式
> `[时间]   [任务名] [级别] 内容` 占 **25,793 行（92%）**，另一种
> `[时间] [级别] 内容` 仅 2,157 行（8%）且**全部是 GUI/调度级消息**
> （`初始化 OCR 引擎…`、`已删除任务…`）—— 它们本就不属于任何任务，没有任务名是对的。
>
> 本报告初版引用的"引擎层格式"样例 `[信息] [自动推图] 任务启动`，经查是
> **2026-09-06 的旧日志**（早于 v1.8.26 的日志规范化）。`loop.py:250` 的
> `_log(level, msg)` 早已转发到**同一张中性级别词表**（`LEVEL_PREFIXES`），
> 两个层的级别词与顺序是统一的。
>
> **结论：无需改动。** 以下原文保留仅作记录。

| 层 | 出口 | 词汇 | 调用点 |
|---|---|---|---|
| 任务层 | `self.log(msg, level)` | 中文级别词 `[信息][成功][警告][错误][点击][数据][配置][调试]` | 394 处 |
| 引擎层 | `self._log(level, msg)` | 英文级别词 `'info' / 'warn' / 'error' / 'debug'`（86/15/10/2 次） | 274 处 |

**后果**（真实日志可见同一场运行两种格式）：

```
[14:31:49] [信息] [自动推图] 任务启动          ← 引擎层：任务名在级别后
[13:32:23]   [自动推图] [信息] 启动            ← 任务层：任务名在级别前
```

**建议**：把 `loop.py:250` 的 `_log(level, msg)` 内部转发到统一出口（映射 `'info'→[信息]`、`'warn'→[警告]`…），格式交给同一个格式化函数。**这是纯展示层改动，不动任何执行逻辑。**

**预期收益**：日志格式统一，GUI 的关键字着色规则对全部 668 个调用点生效（目前引擎层的 274 处无法被正确着色）。

### P0-2 `CRASH_REPORT.log` 被普通 stderr 污染 98%

- 位置：`afk_gui.py:26-30` —— `sys.stderr` 被整体重定向进 `CRASH_REPORT.log`

**预期收益**：崩溃排障从"翻 5,865 行找 34 个块"变成"直接看最后一个块"。

## 四、错误处理与异常信息

### P2-1 52 处 `except` 既不记日志也不上抛

统计：`except Exception` 共 **154 处**，其中 **52 处** catch 后既不 `log` 也不 `raise`。集中分布：

| 文件 | 数量 | 性质判断 |
|---|---|---|
| `tasks/game_launcher.py` | 8+ 处（`:86 :154 :189 :211 :230` 等） | **多为探测型**（找窗口/找启动器），静默可接受，但**缺失诊断信息** |
| `tasks/auto_farm.py:82` `:99` | 2 | 返回 None 的兜底 |
| 其他 | 40+ | 需逐一判定 |

**关键区分**：`base.py:15` 那处带注释的循环导入保护是**合理防御**，不应改。真正的问题是 `game_launcher.py` 这类 —— **"游戏到底启没启动"是用户最关心的问题**，静默失败会让用户看到"启动游戏 完成"却实际什么都没发生。

**建议**：分两类处理 ——
1. **探测型**（预期会失败）：`except Exception as e: self._log('debug', f'探测失败（可忽略）: {e}')` —— 保留静默行为但**留下证据**
2. **不应失败型**：补 `self.log(f'[警告] …异常: {e}')`，让异常可见

**预期收益**：消除"静默失败"这一类最难排查的问题（近期已经踩过两次同类：假成功、吞掉失败返回值）。

### P2-2 20 条「导航失败」错误缺少诊断上下文与行动指引

现有文案全部是**同一句式、只陈述结果**：

```
[错误] 导航失败：未能进入每日任务界面
[错误] 导航失败：未能进入异界迷宫
[错误] 导航失败：未能进入竞技场
… 共 20 个变体
```

用户看到后**无法判断**：是游戏没开？停在了别的界面？还是识别失败？

**建议**：统一为「结果 + 现场 + 建议」。工具里已有现成数据可用 —— `self._last_screen`（最近识别到的画面）：

```
[错误] 导航失败：未能进入每日任务界面 | 最后画面=任务界面 | 建议：确认游戏已打开且窗口可见，重试一次
```

**预期收益**：这类问题从"必须贴日志给我"变成**用户自助定位**。回看本次会话，至少 3 次排障的第一轮对话都用在了"你现在停在哪个界面"上。

### P4-3 裸 `except:` 1 处（低危但应修）

`afk_gui.py:1935`（`_check_admin` 里 `except:`）—— 会吞掉 `KeyboardInterrupt`/`SystemExit`。改为 `except Exception:` 即可。

## 八、一句话总结

代码的**架构与判据体系是健康的**（分层真实、契约明确、单一真相源到位，且已经被真机反复校准），
主要优化空间集中在**日志体系**（占了全部问题的 4 项，且是唯一影响用户日常体验的部分）与
**引擎层的可中断性残留**（用户已经明确要求过"停止要即时"，任务层修了、引擎层没跟上）。
结构性的长函数问题**真实存在但优先级最低** —— 建议先做完 P0/P1，再单独排期拆解。
