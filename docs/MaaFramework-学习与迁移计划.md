# MaaFramework 学习与迁移计划（dev 分支）

> 建立于 2026-11-25，起点 v2.4.21。本文件是 dev 分支的总纲，后续每阶段完成后更新状态。

## 一、目标

让 AFKJ 自动化工具的「识别 + 点击」达到 MaaEnd/MaaFramework 的水平：**单步识别从秒级降到百毫秒级，且判定不发生跨帧漂移**。

## 二、对方强在哪（实测/统计，非印象）

| 机制 | 数据 | 效果 |
|---|---|---|
| ROI 优先 | OCR 54% 带 roi、模板 49% 带 roi；ROI 面积中位数 **30,771 px²（≈175×175）** | 单次识别在极小区域内完成 |
| 等画面静止 | **1212 个节点**用 `wait_freezes`；**7107 个节点** delay 全为 0 | 画面一变就走，不靠固定 sleep |
| 单帧联合判定 | **2074 个 `And`** 节点，一次截图内评估多条件 | 判定对象是同一帧，无跨帧漂移 |
| 复杂逻辑下沉 | 739 Custom 识别 / 1562 Custom 动作（C++ 3.5MB + Go 17MB） | Python 不进热路径 |
| 声明式编排 | 7286 节点 JSON + 参数覆写 | 改行为只改配置 |

## 三、我们的现状（同一台机器实测）

| 操作 | 耗时 |
|---|---|
| 全屏 OCR（1280×1024） | **1501 ms** |
| ROI OCR（400×300） | 597 ms |
| 模板匹配 全屏 × 16 尺度 | **4193 ms** |
| 模板匹配 ROI(400×300) × 16 尺度 | 328 ms |

结构性问题：
1. `ocr_screen()` **没有 roi 参数**，热路径一律全屏；
2. `template_match()` 支持 `region`，但 45 处调用只有 11 处传（**24%**）；
3. 每次匹配都 `np.fromfile` + `cv2.imdecode` 重新解码模板；
4. `click_at()` 尾部硬编码 `sleep(0.5)`；
5. 判据分散在多次快照里，跨帧比较。

## 四、路线（三阶段，逐阶段验收）

### 阶段 1 · 基础设施提速（不改架构，零外部依赖）

| 项 | 做法 | 实测结果（2026-11-25） |
|---|---|---|
| 1.1 OCR 开放 ROI ✅ | `ocr_screen(img=None, roi=None)` 透传到 `MaaOCR.recognize`；缓存键改为 `(指纹, roi)` | 全屏 1501ms → ROI(400×300) 597ms |
| 1.2 模板缓存 ✅ | 按 `(路径, mtime_ns, size)` 缓存解码后的 ndarray | **实测仅省 0.2ms**（原估计 20-40ms 偏高：模板小且已在系统文件缓存里）。保留，无副作用 |
| 1.3 尺度两段式 ✅ | 先扫 `0.9~1.1`（3 尺度），**得分 ≥ max(threshold, 0.75) 才短路**，否则回落全范围 | 命中：3074ms → 533ms（**5.8×**）；未命中：+12%（多跑 3 个尺度）。净收益为正，但因为 ROI 化后绝对耗时才几百 ms，**真正的大头仍是 1.1 的覆盖率** |
| ⚠️ 1.3 的隐患与对策 | 若快扫拿到 0.62 的伪匹配就短路，会漏掉全范围里 0.95 的真匹配 | 故设 0.75 高置信门槛：低分一律回落全范围，**召回率与改动前完全一致**（已用真实模板对比验证：4 个模板新旧结果全部逐位相同） |
| 1.4 点击后等变化 | 以局部帧差替代固定 `sleep(0.5)`，超时兜底 | 待做 |

**原则**：只改 `afk_bot/infra/`，任务层调用点按需补 ROI，行为语义不变，可逐项回滚。

### 阶段 2 · 判定模型重构（仍为自研）

| 项 | 做法 |
|---|---|
| 2.1 单帧联合判定 | 一次 `snap()` 生成 `Frame` 对象，判据在其上组合求值，替代多次独立调用 |
| 2.2 判据表驱动 | 把散落在 22 个任务里的 if/else 收敛为声明式规则表（Python 数据结构，非 JSON 引擎） |
| 2.3 失败留证 | 判定失败时保存帧 + 各判据得分，等价于对方的 `on_error` |

### 阶段 3 · 引擎级方案（**需用户决策，见第六节**）

若要进一步对齐，评估直接引入 MaaFramework 作为识别/动作引擎：任务层改写为 pipeline，我方只保留业务编排。

## 五、AGPL-3.0 边界（必读）

- MaaEnd 与 MaaFramework 均为 **AGPL-3.0**（LICENSE 首行确认）。
- **阶段 1、2 不引入任何对方代码**，只借鉴工程思想（ROI 优先、等静止、单帧联合），因此**当前无需变更本项目许可证**。
- 一旦进入阶段 3（复制代码、或把 MaaFramework 作为运行依赖分发），本项目必须整体转为 AGPL-3.0：
  - 根目录添加 `LICENSE`（AGPL-3.0 全文）
  - `README` 与发布页标注许可证与源码获取方式
  - 分发二进制时提供完整对应源码
  - 保留原项目的版权声明与 NOTICE
- 结论：**先做 1、2 阶段，许可证问题不产生任何义务**；是否进入阶段 3 由用户在阶段 2 验收后再定。
