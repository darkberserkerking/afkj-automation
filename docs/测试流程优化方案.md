# 测试流程优化方案（v1.9.2 基线 · 分析规划稿）

> 结论先行：**耗时不在构建、不在环境、不在用例本身，而在被测代码里被真实执行的
> `time.sleep`**。专项 173 例跑 9~13 分钟，其中绝大部分是干等。把 sleep 在测试态
> 加速掉，是最具性价比的一刀（预计 10~20 倍）。

## 1. 现有流程与实测基线

### 1.1 流程环节（当前串行）

```
改代码 → 备份 → 语法检查(py_compile/pyflakes) → 跑测试(人工选 1~7 个脚本)
      → 人工看输出 → 升版本 → PyInstaller 打包(~60s) → 复制到 D:\桌面
```

没有 CI、没有测试调度脚本、没有并行：每次回归由人工决定跑哪些脚本，实际做法通常是
"全跑一遍"或"挑两三个"，全量串行 ≈ 25~30 分钟。

### 1.2 各环节耗时（实测，2026-09-09 当天多次运行）

| 环节 | 实测耗时 | 占比 | 说明 |
| --- | --- | --- | --- |
| 依赖安装 | 0 | 0% | conda `afk_gpu` 固定环境，日常不重装 |
| 构建（PyInstaller） | ~60 s | 4% | 仅发布时执行，与测试解耦 |
| 语法检查 py_compile/pyflakes | 2~5 s | <1% | 可忽略 |
| **用例执行** | **23~28 min** | **95%** | **唯一瓶颈** |
| 报告生成 | 0 | 0% | 无，靠 stdout |

### 1.3 用例脚本耗时明细

| 测试脚本 | 用例数 | 实测耗时 | 单例均值 | 主耗时来源 |
| --- | --- | --- | --- | --- |
| `test_labyrinth_v1820.py`（专项） | 173 | 9~13 min | ~3.5 s | `_TEXT_TIMEOUT=8s` 重试、`_DOOR_TRANSITION_WAIT=3s`、晶球多轮 sleep |
| `test_labyrinth_nav_dryrun.py` | 133 | ~5 min | ~2.2 s | `GlobalNavigator(poll=1.2s, max_iter=14)` 每轮 sleep |
| `test_global_nav_matrix.py` | 107 | ~3 min | ~1.7 s | 同上，107 组起点×目标 |
| `test_labyrinth_full_round_dryrun.py` | 17 | ~1.5 min | ~5 s | 整轮 1→15 全流程真实 sleep |
| `test_goddess_trial_dryrun.py` | 47 | ~1 min | ~1.2 s | 流程 sleep 16 处 |
| `test_home_task_dryrun.py` | 20 | ~20 s | ~1 s | 愿望单循环 sleep |
| `test_gui_drawer_smoke.py` | 66 | 10~30 s | ~0.3 s | Tk 渲染 |
| `test_task_scheduler_smoke.py` | 17 | ~5 s | — | 纯逻辑 |
| `test_navigator_smoke.py` | 9 | ~5 s | — | 纯逻辑 |

**全量串行合计 ≈ 25~30 min**（今天第 4 次全量回归实测 15 分钟仅跑完 3 个脚本）。

### 1.4 瓶颈定位（量化）

测试脚本自身几乎不含 sleep（各文件 `time.sleep` 计数 0~1），耗时全部来自**被测代码**：

| 文件 | `time.sleep` 调用数 |
| --- | --- |
| `tasks/labyrinth.py` | 56 |
| `afk_bot/services/navigator.py` | 33 |
| `tasks/goddess_trial.py` | 16 |
| `tasks/base.py` | 7 |
| `tasks/home_task.py` | 6 |
| `tasks/global_nav.py` | 11 |

关键等待常量：

| 常量 | 值 | 触发频率 |
| --- | --- | --- |
| `_TEXT_TIMEOUT` | 8.0 s | 每次 `_click_text` 未命中 → 轮询满 8 s |
| `_DOOR_TRANSITION_WAIT` | 3.0 s | 每次点门后 |
| `_BATTLE_WAIT` | 180.0 s | 战斗轮询上限（未命中胜利词时） |
| `_BATTLE_POLL` / `_SKIP_POLL` | 1.2 / 0.45 s | 战斗轮询每轮 |
| `_ORB_SCAN_WAIT` | 0.6 s | 晶球每次下滚 |
| `_TPL_RETRY_WAIT` | 0.6 s | 模板匹配每轮 |
| `GlobalNavigator.poll` | 1.2 s | 导航每轮（max_iter 14） |

→ **结论：把 sleep 加速掉，等于把 95% 的耗时砍掉。**其余优化（并行、增量、分层）
都是在此基础上的二次收益。

## 2. 优化方案

### 措施 1：测试态 sleep 加速（P0 · 最大收益）— ✅ 已落地

- **做法**：新增 `tests/conftest.py`（或在每个测试入口）按模块 monkeypatch：
  `labyrinth.time.sleep = lambda s: None`，同法处理 `global_nav / goddess_trial /
  home_task / navigator`。保留真实时间的白名单：`max_time` 达标用例、deadline 类
  （`_TEXT_TIMEOUT`、`_BATTLE_WAIT` 语义）→ 用可控 fake clock 递增代替空转。
- **预期收益**：专项 9~13 min → 30~60 s；导航 5 min → ~20 s；矩阵 3 min → ~15 s。
  全量 25~30 min → **3~5 min（10 倍级）**。
- **成本**：低（纯测试侧，1 个 conftest + 少量用例适配白名单）。
- **风险**：削弱"真实时序"覆盖（如转场等待 3 s 是否真够）→ 缓解：发布级跑一次全真实
  时间版本；`max_time`/deadline 用例强制真实计时。

### 措施 2：用例分层分级（P0）— ✅ 已落地

| 级别 | 触发时机 | 内容 | 目标时长 |
| --- | --- | --- | --- |
| L1 本地/提交级 | 每次改代码 | 语法检查 + 调度器 + navigator + 家园 + GUI 冒烟 + 专项快速子集 | < 60 s |
| L2 PR 级 | 提交前 | L1 + 专项全量 + 导航 + 女神 + 整轮 | < 3 min（配合措施 1） |
| L3 发布级 | 打包前 | L2 + 矩阵 107 + 全真实时间跑一遍专项 + 打包 | < 10 min |

- **成本**：低（写一个 `tests/run_tests.py --level=1|2|3` 调度脚本）。
- **风险**：分级漏测 → 缓解：核心目录（`tasks/`、`afk_bot/`）任何改动强制 L2 起。

### 措施 3：并行与分片（P1）— ✅ 已落地（文件级并行 + --shard）

- **文件级并行**：`run_tests.py` 用 `concurrent.futures` 同时跑互不相关的脚本
  （专项 / 导航 / 女神 / 家园 / 矩阵），GUI 类因 Tk 独占单独串行。
- **用例级分片**：专项 173 例按用例组（A~F / G~P / Q~Z / AA~AF）切成 4 片并行，
  需把脚本改造成 pytest 用例（`test_*` 函数）或加 `--shard` 参数。
- **预期收益**：叠加措施 1 后，L3 从 3~5 min 再降到 **1~2 min**。
- **成本**：中（脚本改造）；用例间无共享状态（各测自建 MockBot + 临时 config），
  可并行性良好。

### 措施 4：按变更范围增量筛选（P1）— ✅ 已落地（--changed）

文件 → 测试映射表（`run_tests.py` 内置）：

| 改动文件 | 必跑 |
| --- | --- |
| `tasks/labyrinth.py` | 专项 + 导航 + 整轮 |
| `tasks/global_nav.py`、`tasks/screen_registry.py` | 矩阵 + 导航 + 专项（判据敏感） |
| `tasks/home_task.py` | 家园 |
| `afk_gui.py`、`task_registry.py`、`tasks/scheduler.py` | GUI 冒烟 + 调度器 |
| `afk_bot/**`、`tasks/goddess_trial.py` | 对应干跑 + L2 兜底 |
| `templates/*.png` | 专项（模板相关 W 组）+ 矩阵 |

- **预期收益**：日常单文件改动只需跑 1~2 个脚本（< 60 s）。
- **成本**：低-中（`git diff --name-only` + 映射表）。
- **风险**：映射遗漏 → 缓解：未命中映射默认跑 L2；发布前强制 L3。

### 措施 5：慢用例与重复用例改造（P1）

> **落地决定（v1.9.2）：只做画像 + 降级，不做用例级合并。**
> 理由：措施 1 落地后全量已降到 6 秒，合并用例的收益从「省分钟」变成「省毫秒」，
> 而重构 173 条断言的回归风险显著高于收益——成本收益比已逆转。保留三项：
> ① `--slow-report` 脚本级耗时画像；② 整轮干跑（与专项覆盖重叠）降级到 L3；
> ③ 重复帧构造清单留待未来 pytest 参数化改造时一并处理。

- 专项里大量用例复用同一帧序列重复构造（如 `step1_items` + `_orb_frame(...)` 组合），
  可参数化合并（`@pytest.mark.parametrize`）→ 减少重复构造与重复流程跑。
- 整轮干跑（1→15，~1.5 min）与专项存在覆盖重叠 → 整轮并入 L3，PR 级不跑。
- **预期收益**：专项用例数 173 → ~120，再省 20~30%。
- **成本**：中（重构用例，需谨慎避免改坏断言）。

### 措施 6：不稳定用例隔离（P2）— ✅ 已落地（--retry + --quarantine）

- 对偶发失败用例（OCR 帧依赖、时序敏感）打 `@pytest.mark.flaky` + 重试 2 次；
  连续 3 次失败自动隔离到 `tests/quarantine/` 并出报告，不阻塞回归。
- **成本**：中；**收益**：降低"假红"导致的重复全量重跑（今天就有一次因 R2 回归
  重跑专项 9 分钟）。

### 措施 7（长期）：生产代码 sleep 钩子化（P2）— ✅ 已落地（85 处 → self._sleep）

- 把 `tasks/**` 里 56+ 处裸 `time.sleep` 收敛为 `self._sleep(sec)`（BaseTask 提供，
  默认真实 sleep），测试注入 no-op。比 monkeypatch 更彻底、可维护。
- **成本**：高（改动面大，需逐处验证）；**收益**：可测性根本改善，未来新增代码
  天然可加速。建议随功能迭代渐进替换，不专门开大改。

## 3. 优先级与落地顺序

| 顺序 | 措施 | 成本 | 预期收益 | 覆盖/可靠性影响 |
| --- | --- | --- | --- | --- |
| 1 | 测试态 sleep 加速 | 低 | 10~20× | 时序覆盖削弱 → 发布级补真实时间 |
| 2 | 分层分级 + run_tests.py | 低 | 日常 <60 s | 分级漏测 → 核心改动强制 L2 |
| 3 | 文件级并行 + 增量筛选 | 中 | 再省 50% | 低（用例无共享状态） |
| 4 | 慢/重复用例合并 | 中 | 再省 20~30% | 中（重构需重验断言） |
| 5 | flaky 隔离重试 | 中 | 减少假红重跑 | 正面 |
| 6 | 用例级分片（xdist） | 中 | 大仓后收益递增 | 低 |
| 7 | 生产 sleep 钩子化 | 高 | 长期可测性 | 正面，但需渐进 |

**短期（1~2 次迭代可完成）**：措施 1、2、3（增量筛选）→ 全量从 25~30 min 压到
3~5 min，日常改动 <60 s。
**长期（随迭代推进）**：措施 4~7。

## 4. 建议的验收指标

- L1（本地/提交）< 60 s
- L2（PR）< 3 min
- L3（发布，含打包）< 10 min
- 覆盖率不降：L3 必须等同于今天的全量集合（含真实时间专项一遍）
