### 1.3 B. MaaOCR `recognize()` 全图耗时

- 初始化（CPU ORT）：0.25 s（一次性）
- 5 张图 × 5 次均值：**451.1 ms / 次**，最大 501.1 ms

入口：`_ocr_screen` → `ScreenCapture.ocr_screen` → `_ocr_img` → `OcrEngine.recognize(img, roi=None)`（详见 `afk_bot/infra/screen.py:404`）。注意 `ocr_screen` 内置 60 秒**画面指纹缓存**（`_ocr_fingerprint`，`afk_bot/infra/screen.py:455`），但战斗画面每秒都在变（倒计时跳动/技能特效），缓存基本不会命中，所以每次都走完整 `recognize`。

## 二、真实采样间隔推算

只测得 A 和 B。`time.sleep(_BATTLE_POLL)` = 1.2 s。单轮真实耗时（不含 snap）：

```
loop = 1.2 + A + B
```

| 配置 | A (ms) | B (ms) | loop (s) | 13s 战斗可采样 | 采样点（按 F 后秒数） |
|---|---:|---:|---:|---:|---|
| **现网 9 档** | 3373 | 451 | **5.02** | **3 次** | 5.0, 10.0 |
| 收窄 5 档 | 1883 | 451 | 3.53 | 4 次 | 3.5, 7.1, 10.6 |
| 收窄 3 档 | 1129 | 451 | 2.78 | 5 次 | 2.8, 5.6, 8.3, 11.1 |

加上估计的 2×200 ms `snap`，现网单轮 ~5.4 s，13 s 内仍只采 2-3 次。

> 关键：用户日志中命中时刻都集中在按 F 后 11-12 s——而**现网第 2 次采样才在 10 s 出现**（10.0 s），能否刚好命中纯靠运气。如果胜利弹层在 11-12 s 之间闪现，跳过按钮可能只存在 0.x-1 s 而被漏掉。如果战斗拖到 18 s 才胜利（用户实测的 14:49 场），前 4 次采样中任何一次恰好落在 10-18 s 倒计时末尾都可能赶上；问题是 18 s 内 9 档只采 4 次、5 档 5 次、3 档 6 次，命中率分别只有 25%/33%/42%。

## 三、跳过按钮出现时机分析

从用户真机日志：

```
14:47:37 备战画面 → 按 F 开始战斗
14:47:49 战斗中出现「跳过」，点击快进   （按 F 后 12s）
14:47:51 战斗胜利弹层已出现            （按 F 后 14s）
14:49:40 备战画面 → 按 F 开始战斗
14:49:58 战斗胜利弹层已出现            （按 F 后 18s，全程未命中）
14:50:18 备战画面 → 按 F 开始战斗
14:50:29 战斗中出现「跳过」，点击快进   （按 F 后 11s）
14:50:32 战斗胜利弹层已出现            （按 F 后 14s）
```

### 推断

- **可观察到的最早命中时刻 = 11 s**（14:50:29 场），且两次命中到胜利弹层出现都只差 2-3 s。
- **按钮存在的窗口最长 3 s**（11-14s / 12-14s）。
- 14:49 场战斗拖到 18 s 也未命中，说明跳过按钮**可能在该场战斗中根本没出现**（可能是 Boss 战没有"跳过"机制，或者 4 倍速下快进按钮被游戏端隐藏）；也可能是按钮存在但被 5 s 一次的轮询漏掉。

### 关键问题：按钮从战斗一开始就存在吗？

**不能确证**。已知信息：
1. 命中最早 11 s + 按钮存在窗口 2-3 s → **命中区间落在 11-14 s**。但这是观测的下界。
2. 战斗开始通常有一段"出现-交战-读秒"过程：按 F → 双方入场动画（1-2 s）→ 4x 加速（用户定 4 倍速）→ 战斗读秒开始（82-86 s）→ 约 11-14 s 末段因血量见底触发"可跳过"提示。
3. 视觉上的"跳过"按钮是"快进"功能——通常只在倒计时剩余不多时（<10 s 量级）出现。14:49 场 18 s 才胜利、跳过仍未出现，**间接支持"按钮仅在最后 5-10 s 出现"**。

**结论**：
- 跳过按钮**可能从战斗一开始就存在**这一假设**证据不足**——14:49 场若按钮一直在，5 s × 3 次采样（5/10/15 s）中有 2 次落在按钮存在窗口内，应能命中却没命中。
- 更合理的假设：**按钮只在战斗末段（胜利前数秒）才出现**（典型的"快进"设计）。这意味着任何"采样到恰好 11 s+ 时刻"的策略都能命中；问题就是**采样太稀疏，正好卡在 11-14 s 的概率太低**。

## 四、改进方案评估

### 4.1 方案① 收窄 scale_range

| 配置 | A 耗时 | 13s 采样 | 提速 | 风险 |
|---|---:|---:|---:|---|
| (0.7, 1.5, 0.1) 9 档 | 3373 ms | 3 | 1.0x | 现网 |
| (0.9, 1.1, 0.05) 5 档 | 1883 ms | 4 | 1.8x | 低——战斗截图 3 张都 scale 1.0 命中 |
| (0.95, 1.05, 0.05) 3 档 | 1129 ms | 5 | 3.0x | 中——若按钮实际有 ±5% 缩放会漏 |

**结论**：可独立受益，但仍是治标。**推荐保留 5 档（0.9-1.1）** 作为区域限定时的保底缩放带——按钮实测全在 scale 1.0，但 5 档给 ±10% 缓冲。

### 4.2 方案② 独立子循环（高频模板 + 低频 OCR）

把"按 F 后等待战斗结束"拆成两个节奏：
- **快速子循环（仅做模板匹配）**：每 0.4-0.5 s 跑一次 maskedNCC，命中即点跳过。
- **慢速主循环（含 OCR）**：每 2-3 s 跑一次 OCR 判定 victory/failure。

按 0.45 s + region 5 档 = 0.45 + 0.064 = 0.514 s/轮 → **13 s 内可采样 25 次**。按 0.5 s + region 5 档 = 0.56 s/轮 → 24 次。

**预期收益**：跳过按钮存在 3 s 的窗口内至少能踩中 6-8 次，几乎必中。OCR 仍然能 2-3 s 检测一次胜利/失败，不影响结果判定。

**额外注意**：OCR 自身有 60s 缓存（画面指纹）但战斗画面每帧都在变，基本不命中，OCR 仍是真成本——但频率从 0.7 Hz（现网）降到 0.3 Hz 后省下的成本进一步缩短主循环总耗时。

### 4.3 方案③ region 限定（推荐组合中的关键）

按钮稳定在右下偏内，**3 张真机截图中心都在 (885, 809)，比例 (0.690, 0.789)**：

- 按钮 63×75（含 49.5% 透明 mask）→ 全屏位置面积 vs 区域面积比 ≈ 1.21M / 14.4k = **84×**。
- 实测 region 5 档 maskedNCC：**64 ms**（vs 全屏 9 档 3373 ms，**52× 提速**）。

**安全 region 比例（不绑死像素）**：
```
x 比例 ∈ [0.62, 0.77]    # 192 px @1280
y 比例 ∈ [0.70, 0.88]    # 185 px @1024
```
padding 约 ±40 px，留给 scale 1.0±5% 的伸缩空间。验证：3 张战斗截图在 region 内**全部** val 0.99+ 命中（val=0.999, 1.000, 1.000），非战斗画面在 region 内均 < 0.32（无虚假命中）。

**注意**：region 用比例表达，不绑死像素——若将来真机分辨率变化（1920×1080、1366×768 等），比例仍适用，前提是「真机历史素材分辨率与本机一致」这个事实不变（详见 §1.5 注）。

### 4.4 方案④ 其它瓶颈

1. **截图双倍调用**（`template_match` 和 `ocr_screen` 各自 `snap()`）。如果同帧内复用截图，理论上能省一次 snap（~50-200 ms）。但这要改 `template_match` 和 `ocr_screen` 的接口契约，影响面大，独立收益相对 region 化太小。
2. **MaaOCR `DET_LIMIT_SIDE_LEN = 736`**（`maa_ocr.py:55`），整图 1280×1024 会被缩到短边 736。det 模型主时间花在缩放后 736×589 图像的卷积推理上。降低整图 OCR 频率（方案②的子循环只做模板、不调 OCR）是性价比最高的省 OCR 路径。
3. **战斗开始动画 1-2 s 内是入场画面**（无跳过按钮）。如果子循环从按 F 后 1-2 s 才开始能省一些，但当前 sleep(1.2) 已经把首轮推后了。
4. **14:49 18s 全程未命中**：可能并非纯采样问题，而是该场战斗没有"跳过"机制（深層首領战玩家口述无快进）。如果该情况真实存在，再优化采样也不会 100% 命中——这是**业务规则上的硬约束**，需要用户先确认 14:49 场是否真无跳过按钮。

## 五、推荐组合

**方案②+③ 联合**（收益最大、风险最低）：

```text
# 伪代码（仅示意，不动源码）
SKIP_REGION = (0.62, 0.70, 0.77, 0.88)   # 比例 (rx0, ry0, rx1, ry1)
SKIP_SR     = (0.9, 1.1, 0.05)            # 5 档
FAST_SLEEP  = 0.45                        # 子循环 sleep
SLOW_EVERY  = 3                           # 每 3 轮 OCR 一次

while time.time() < deadline:
    if check_stop(): return
    pos = bot.template_match(tpl, thr=0.72, region=SKIP_REGION, scale_range=SKIP_SR, silent=True)
    if pos:
        bot._click_abs(*pos)
        time.sleep(1.5)  # 跳过动画

    # OCR 降频：3 轮做一次
    if loop_n % SLOW_EVERY == 0:
        items = bot._ocr_screen()
        # 状态判定（胜利/失败/上弹/转换）...
    else:
        time.sleep(FAST_SLEEP)
```

**预期**：
- 跳过命中：13 s 战斗内可踩 24-28 次模板采样，3 s 存在窗口必有命中
- OCR 成本：3.3 Hz（现网 0.7 Hz）→ 5× 节省
- 模板匹配成本：64 ms/次（region 5 档）→ 53× 节省 vs 现网 3373 ms
- 单循环真实耗时：0.45 + 0.064 + (0.45/3 × 0.45 OCR) ≈ 0.57 s/轮

**region 比例**（如果 4.3 比例命中但用户改用像素）：

| 分辨率 | 像素 region (x, y, w, h) |
|---|---|
| 1280×1024 | (793, 717, 193, 184) |
| 1366×768 | (847, 538, 206, 138) |
| 1920×1080 | (1190, 756, 289, 194) |

**强烈建议用比例**而不是像素，与 `docs/坐标规范.md` "1280×1024 假设需集中到 CoordSystem"的遗留建议一致。

## 六、结论摘要（给 team-lead 答话用）

- **A. maskedNCC 全屏 9 档**：均值 **3373 ms**（max 3632）；5 档 **1883 ms**（1.79x）；3 档 **1129 ms**（3x）。
- **B. MaaOCR 整图**：均值 **451 ms**（max 501）。
- **13s 战斗采样次数（不含 snap）**：现网 **3 次**（@5.0/10.0s）；5 档 4 次；3 档 5 次。
- **按钮位置**（3 张真机截图，比例 0.690×0.789 稳定，±1px）：推荐 region 比例 **x∈[0.62,0.77] y∈[0.70,0.88]**，对应 1280×1024 像素 (793, 717, 193, 184)。region 5 档实测 **64 ms**（52x 提速）。**不要绑死像素**，比例跨分辨率通用。
- **按钮出现时机**：不能确证"从一开始就存在"。14:49 场 18 s 仍未命中**强烈反证**"按钮全程存在"假设；更可能是战斗末段（胜利前数秒）才出现。日志两次命中都在 11-12 s 区间。
- **推荐组合**：**方案②+③ 联合**——region 限定 + 5 档缩放 + 0.45s 高频子循环 + 每 3 轮做 1 次 OCR。**不要单用方案①**（仍太稀疏）；**不要单用方案③**（不解决 OCR 占用）。
- **遗留疑点**：14:49 18s 场若按钮真的没出现，采样再密也无效——需用户先确认该场是否真有跳过按钮。
